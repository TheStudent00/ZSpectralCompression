# log 012 — ZSC against mp4 on a real video clip

Repo: ZSpectralCompression. Written 2026-09-25 by Claude (Opus 5.5).
Every computation ran in Airlock's default sandbox. Tools added:
`Tools/video_vs_mp4.py` (runs every method on one clip and records the
results) and `Tools/plot_rate_quality.py` (draws Figure 1 from that
record).

The owner, 2026-09-25:

> have we tried compression on actual video? i assume that some Python
> API has it. if not, i can get a video for us. i want to see how it
> compares to mp4.

---

## 1. What was done, in plain words

Before today, no real video had been tried. Every "video" in logs 010
and 011 was a small block of numbers generated by a script: a still
texture repeated, a fading texture, a moving disc, and one photograph
slid sideways one pixel per frame.

Today one real clip went through ZSC and through the codecs mp4 files
use. The clip is a 4-second, 1280x720 recording of a bee on a thistle,
shipped as a sample asset with the Flutter gallery package (it is not
committed here). To keep this a small verification run, only the
brightness channel was used, shrunk five times in each direction by
averaging 5x5 pixel blocks, and cropped to the middle 128 rows: 64
frames of 128 rows by 256 columns, 2,097,152 bytes raw.

Every method compressed exactly those bytes. Every size below is a
real byte count. For the lossless methods, every pixel was checked to
come back; for the lossy ones, closeness to the original was measured.

The short answer: on this clip ZSC loses to mp4 clearly, in both
senses. Section 4 shows why with the clip's own numbers.

## 2. The words this log uses

`ZSC`
- ZSpectralCompression: it reads a block of data into one long line,
  cuts the line into short runs, and stores each run as a small curve.
- The lossless version (`src/zsc_lossless.py`) also stores the small
  corrections that make every value exact.

`segment`
- One of those short runs, described by one curve.

`reading order`
- How ZSC walks a video block (vertical x horizontal x time) to make
  the long line. Logs 010 and 011 call this the "traversal order".
- `time-first`: one pixel spot's value in frame 1, 2, 3 ... 64, then
  the next spot.
- `horizontal-first`: along each row of each frame.
- `vertical-first`: down each column of each frame.
- `Morton`: a 2x2x2 cube of neighbours (2 rows x 2 columns x 2
  frames), then the next cube, then groups of cubes, zig-zagging, so
  values that sit close in space and time stay close in the line.

`ratio`
- The raw size divided by the compressed size. 2.00x is half the
  size; below 1.00x the file grew.

`xz -9`
- `xz` is the general-purpose file compressor built into Linux, doing
  the same job as zip. `-9` is its "try hardest" setting.
- It finds byte strings that already appeared earlier in the file and
  replaces each repeat with a pointer back to it. It knows nothing
  about pictures, which is why it serves as the baseline.

`mp4`, `H.264`, `crf`
- mp4 is the file wrapper; H.264 is the compression inside almost
  every mp4. `libx264` is the standard program that does H.264.
- `crf` is libx264's quality dial: lower is closer to the original and
  bigger. 23 is its default, so "crf 23" is what a typical mp4 is.

`FFV1`
- A video format built to be lossless: the fair lossless opponent.

`PSNR`
- How close a lossy result is to the original, in decibels: take each
  pixel's error, square it, average the squares, and compare that
  average with 255 squared (PSNR = 10 log10(255^2 / mean squared
  error)).
- Around 30 dB shows visible damage, around 40 dB is hard to see,
  identical is infinite.

`addressable` and `sequential`
- ZSC's two ways to store its result. Addressable: any segment can be
  read alone. Sequential: the whole result squeezed again with xz,
  smaller, but read from the start, the way an mp4 is.

## 3. Results

### Table 1 — lossless: every pixel comes back

| method | bytes | ratio | seconds to compress |
|---|---|---|---|
| raw frames, no compression | 2,097,152 | 1.00x | — |
| **H.264 lossless, in .mp4** | **720,763** | **2.91x** | 0.1 |
| FFV1, in .mkv | 905,373 | 2.32x | 0.1 |
| xz -9 on the raw frames | 1,097,744 | 1.91x | 0.6 |
| ZSC lossless, sequential | 1,254,533 | 1.67x | 19.3 |
| ZSC lossless, addressable | 1,616,285 | 1.30x | 18.9 |

ZSC chose the Morton reading order for both. H.264's lossless mode is
1.74 times smaller than ZSC's sequential result, and ZSC does not beat
plain xz on this clip.

### Table 2 — lossy: what a normal mp4 is

| method | bytes | ratio | PSNR |
|---|---|---|---|
| H.264 crf 18, .mp4 | 86,482 | 24.25x | 40.16 dB |
| **H.264 crf 23, .mp4 (a typical mp4)** | **46,230** | **45.36x** | **36.82 dB** |
| H.264 crf 28, .mp4 | 25,630 | 81.82x | 33.73 dB |
| H.264 crf 33, .mp4 | 14,767 | 142.02x | 30.78 dB |
| ZSC lossy (the prototype), threshold 0.002 | 658,604 | 3.18x | 42.01 dB |
| ZSC lossy (the prototype), threshold 0.005 | 561,948 | 3.73x | 41.62 dB |
| ZSC lossy (the prototype), threshold 0.01 | 465,748 | 4.50x | 40.52 dB |
| ZSC lossy (the prototype), threshold 0.02 | 363,496 | 5.77x | 37.93 dB |

ZSC's lossy sizes are the prototype's payload (segment labels, mean
levels, codebook, segment-length bitmask) written out as real bytes
and squeezed by xz. The prototype's own count, which does not squeeze,
is larger: 1,056,462 bytes at threshold 0.002 down to 444,711 at 0.02.

At matched closeness, about 40 dB: H.264 crf 18 is 86,482 bytes and ZSC
at threshold 0.01 is 465,748 — **H.264 is 5.4 times smaller.**

## 4. Why ZSC loses here

### 4.1 No pixel spot holds still

Each pixel spot's spread across the 64 frames (largest brightness
minus smallest), over all 32,768 spots:

| how much the spot changes over 64 frames | spots | share |
|---|---|---|
| never changes | 0 | 0.0% |
| by 1–2 levels | 0 | 0.0% |
| by 3–8 levels | 6 | 0.0% |
| by 9–32 levels | 7,493 | 22.9% |
| by more than 32 levels | 25,269 | 77.1% |

One spot in the blurred background (row 20, column 30), its first 16
frames:

    130, 130, 130, 132, 133, 136, 139, 141, 141, 142, 142, 142, 142, 141, 139, 137

The synthetic "static scene" of log 010, which reached 24.98x with
time-first reading, had every spot perfectly still. This real clip is
the opposite: the camera drifts, the flower sways, the bee moves.

### 4.2 So time-first does not win, and Morton only a little

ZSC's own estimate for each reading order on this clip (addressable
container):

| reading order | estimated bytes | ratio |
|---|---|---|
| Morton | 1,441,354 | 1.45x |
| time-first | 1,667,972 | 1.26x |
| vertical-first | 1,687,266 | 1.24x |
| horizontal-first | 1,701,307 | 1.23x |

### 4.3 What H.264 does that ZSC cannot: follow the motion

H.264 predicts each small block of a frame from a *shifted* block of
an earlier frame, "the same patch as last frame, moved 3 pixels left",
and stores only what that prediction missed plus the shift. ZSC has no
way to say "moved"; its curves run along a fixed reading order.

Measured on this clip, 8x8 blocks over 63 frame pairs, the average
brightness change per pixel that is left to store:

| each block compared with | average change per pixel |
|---|---|
| the same place in the last frame | 5.68 levels |
| one shift of the whole frame, the best one | 4.43 levels |
| its own best-matching place, shifted up to 4 pixels | **2.70 levels** |

Following each block's own motion halves what is left to store. That
is the single largest thing mp4 has that ZSC lacks.

### 4.4 Segments stay short

At threshold 0.002 the prototype used 468,173 segments for 2,097,152
pixels: about 4.5 pixels per segment. At 0.02, 196,284 segments:
about 10.7 pixels per segment. Log 007 §8 measured the same thing on
text: when segments are this short, describing the curves costs
nearly as much as the pixels themselves.

## 5. What this run does not establish

- **The clip was already H.264-compressed once**, when it was made.
  Its finest detail and camera noise were already removed by an H.264
  encoder. Shrinking by 5x5 averaging breaks up that encoder's block
  grid, but a fair test starts from an uncompressed recording.
- Brightness only. Colour doubles the work for every method, roughly
  equally.
- One clip, 64 frames, small. A clip filmed on a tripod with a still
  background is the case most favourable to time-first reading, and
  none was tried.

## 6. A defect found in `src/zsc_lossless.py` — status: open

The addressable result (1,616,285 bytes) is 12% larger than the
codec's own estimate (1,441,354). The cause: each curve coefficient is
written as a 32-bit integer (`coef_blob.write(q[i].astype("<i4")...)`
in `ZSCLossless.compress`), although it was quantised to 8, 12 or 16
bits and priced that way. Packing them at their real width closes the
gap. It does not change any conclusion above: 1.45x is still half of
H.264's lossless 2.91x.

## 8. What this means

- **Research.** ZSC's time axis pays only where pixel spots hold
  still. Real footage from a moving or hand-held camera needs a motion
  model: shift each block before fitting curves, or pick the reading
  order region by region (log 011 §4, still open). Without one, mp4 is
  5.4 times smaller at the same closeness.
- **Next.** The same run on an uncompressed recording, full size and
  in colour, including one tripod clip, so the result is not shaped by
  an earlier encoder.
